# 安卓客户端两份 SRE Performance 报告分析（2026-11-13）

## 结论

**主要瓶颈是 GL4ES / Krypton Wrapper 图形链路中的材质动画上传和顶点提交，不是已证实的某一款模组独占 CPU，也不是单纯被限帧锁住。**

第二份为完整的前台、世界内、无界面采样，平均 42.51 FPS，约 10.36% 的帧间隔超过 50 ms。两个上传作用域的 self 墙钟时间合计约 31.39 秒，占已记录根帧时间约 52.35%；其中纹理上传导致了一次约 241 ms 的明确长帧。其他模组有开销，但现阶段不建议优先大面积删除 VoiceChat、ModernUI 或职业内容。

这比先前父子权重异常的 Spark 文件提供了更可靠的阶段证据；仍没有 GPU 硬计时、温度/频率或单模组停用 A/B，不能据此宣布某模组存在 Bug 或承诺删除收益。

## 1. 真实运行环境

两份均来自同一类安卓环境：Android 16 / ARM64，Java 21，Mali-G720 MC8，GL4ES `libng_gl4es.so`，图形版本字符串显示 `Krypton Wrapper Release 0.4.5`。这里的 Wrapper 是图形后端标识，不能因此归咎于整合包中同名的 Krypton 网络优化模组。

实际窗口 framebuffer 为 **2800×1260（352.8 万像素）**，首尾未变。视距 4、模拟距离 5、FAST 画质、粒子 ALL；**光影包未启用**。因此不能把这些低帧归咎于开启了 Complementary 等外部光影。

两份都记录垂直同步开启，第一份开始时帧率上限 60，第二份为 240。设置只在采集开始读取一次，不保证全程未改，也未验证转译后端是否严格执行垂直同步。

## 3. 第二份：一半以上根帧时间在上传入口内部

分母为 FRAME 已记录墙钟时间 59.949 秒。self 排除了直接子计时作用域，可用于下列不重叠分解；不是 GPU 使用率，也不是某个模组独占 CPU 时间。

| 作用域 | self 墙钟时间 | 根帧时间占比 | 补充 |
| --- | ---: | ---: | --- |
| 纹理上传 | 17.311 秒 | 28.88% | 5750 次；平均每次约 3.01 ms |
| 顶点上传 | 14.075 秒 | 23.48% | 81,255 次；平均每帧约 31.86 次 |
| 世界渲染其余 | 12.801 秒 | 21.35% | 排除已单列的直接子阶段，仍含绘制/状态等工作 |
| 客户端 Tick 其余 | 4.872 秒 | 8.13% | 不重复加入纹理、声音和粒子子阶段 |
| 声音播放 self | 3.784 秒 | 6.31% | 包含声音任务等待，不能全算声学计算 |
| 限帧等待 | 0.234 秒 | 0.39% | 不是本次持续低帧的主要耗时 |

`render` 包含 `world_render` 和其中的上传，不能再与这些项相加。声音 Tick 与声音播放也有嵌套，不能将 3.53+3.86 秒当作独立的 7.39 秒。

### 3.1 材质动画上传是最明确的长帧来源之一

实际链路：

```text
Minecraft.tick
  → Stfu.shouldTickTextures 包装
  → TextureManager / TextureAtlas 动画更新
  → SpriteContents 动画帧上传
  → NativeImage._upload
  → glTexSubImage2D
```

- 累计上传钩子时间 17.31 秒，材质动画作用域合计 17.35 秒；动画作用域 self 只有约 87 ms，主要时间落在最终上传入口而非已单列的外层动画逻辑。
- 记录的纹理请求量约 **4.60 MiB/60 秒**，不是几 GB 的大材质传输。与长耗时结合，更值得检查转译/驱动提交、同步和调用开销；不能简单解释为“带宽被大贴图占满”。这些是引擎入口的请求字节，不是硬件总线流量。
- 采集开始后约 10.056 秒的第 582 帧工作时间约 **240.94 ms**，该帧纹理上传累计约 **216.42 ms**；单次上传最大约 216.23 ms，下一帧起点间隔约 240.98 ms。
- 渲染线程 1184 个样本中，279 个直接落在 `nglTexSubImage2D`，占该线程样本约 23.56%，与阶段证据共同支持该路径确实很重。

这证明了动画上传路径的成本，**没有证明 Stfu 自身占了 23.9% CPU**；它只是这里最近的模组包装层。应先对照装饰性动态材质/动画策略，再判断 Stfu 是否影响调用频率。

### 3.2 顶点提交 / Iris / ImmediatelyFast 是另一条主路径

实际链路：

```text
世界渲染
  → Iris FullyBufferedMultiBufferSource.endBatch
  → VertexBuffer 上传
  → ImmediatelyFast.optimizeVertexDataUploading
  → glBufferSubData
```

- 引擎上传钩子合计约 **14.07 秒**，约 **5.52 ms/帧**；请求顶点/索引数据约 **673.52 MiB/60 秒**。
- 314/1184 个渲染线程样本直接落在 `nglBufferSubData`（约 26.52%）。
- 约 27.563 秒的一帧工作约 102.99 ms，其中顶点上传累计约 59.65 ms，另有纹理上传约 19.31 ms。

即使光影关闭，Iris 的实体合批路径仍然在运行。ImmediatelyFast/Iris 是值得做安卓兼容性对照的组件，但“经过它们的路径重”不等于“它们比不装更慢”或“二者冲突”。当前未做移除对照。

按帧间隔终点划分的近似十秒窗口：

| 采集区间 | 平均 FPS | 顶点上传平均 ms/帧 | 纹理上传平均 ms/帧 |
| --- | ---: | ---: | ---: |
| 0–10 秒 | 57.98 | 3.86 | 4.74 |
| 10–20 秒 | 57.59 | 3.59 | 4.79 |
| 20–30 秒 | 63.54 | 3.62 | 4.07 |
| 30–40 秒 | 28.71 | 7.27 | 11.32 |
| 40–50 秒 | 28.33 | 8.55 | 12.17 |
| 50–60 秒 | 18.85 | 15.71 | 13.35 |

全程前台且没有打开界面，但没有记录镜头、场景实体数量、硬件频率和温度；无法区分走进复杂场景、后台系统争用、硬件降频等原因。**“可能热降频”不能写成已证实结论。**

约 50.255 / 50.434 秒还有两帧，世界渲染分别约 141.23 / 161.22 ms，并非所有长帧都由纹理上传单独解释。该采集器没有逐帧、逐模组的完整时间线，不能把这些特定长帧准确分配给某个角色或玩家模型。

长帧归因已将第 i 行的间隔与第 i−1 帧的工作对齐，没有误用同一行的当前帧工作解释之前的间隔。

## 4. 哪些模组值得处理，哪些不能按排行榜下结论

以下是第二份的渲染线程“最近模组路径”样本占比，不是独占耗时：

| 模组 | 最近路径样本占比 | 正确解读 |
| --- | ---: | --- |
| ImmediatelyFast | 27.70% | 大量样本实际在原生顶点上传；优先做该上传路径的后端/兼容性对照 |
| Stfu | 23.90% | 主要包住原版动态材质更新，不代表其自身逻辑消耗 23.90% |
| Sodium Extra | 7.77% | 世界渲染包装层也会被关联，不能把整个世界渲染成本算给它 |
| SRE 本体 | 7.01% | 包含手持物品判定、皮肤查询、玩偶身份/背包扫描；有优化候选，但不是当前已测最大的两个阶段 |
| Iris | 6.84% | 实体合批/提交路径，未启用外部光影仍可运行 |
| Dynamic Surroundings | 2.79% | 地雾等实际工作存在，同时有包住原版绘制的包装层；不能用包含式路径认定它承担大部分渲染 |
| ModernUI | 0.08% | 本次纯实玩采样没有支持它是主要根因的证据；不代表所有界面都廉价 |

SRE 具体保留下来的路径包括：

```text
玩家手持物品/手臂判定
  → AllowItemShowInHand
  → MorphApiClient.getDisplayedPlushStack
  → PlushEquipmentManager.findIdentityPlush / collectInventories

玩家皮肤查询
  → OnGettingPlayerSkin / applySkinSwap
```

这是后续优化的具体候选，不需要凭空把全部压力归给外部模组；不过目前没有这些函数的独占计时或无诊断器对照，不能承诺缓存后提升多少 FPS。

### VoiceChat 的“100%”不是占满 CPU

第二份采到的语音频道线程中，2289/2308 个样本（约 **99.18%**）处于 WAITING/TIMED_WAITING，主要是在等音频包。某线程所有调用栈都属于 VoiceChat，便会显示 100% 模组关联；这不是系统 CPU 100%。

声音播放确实有约 3.78 秒 self 墙钟工作/等待，是次级方向。**第二份没有采到真正的 `Sound engine` 线程**：采集器的最多三个音频目标名额被名字排序更靠前的音频/语音线程占用。第一份有声音线程样本，第二份不足以进一步区分 OpenAL、声学射线或其他声音任务。因此不应优先凭“100%”删掉语音，也不能宣称物理声效完全无影响。

## 5. 内存与诊断器开销

| 项目 | 第一份 | 第二份 |
| --- | ---: | ---: |
| Java 堆上限 | 2048 MiB | 2048 MiB |
| 每秒快照观察到的堆峰值 | 1904.75 MiB（93.01%） | 1921.06 MiB（93.80%） |
| Young GC | 5 次 / 190 ms | 11 次 / 396 ms |
| Concurrent GC | 4 次 / 79 ms | 6 次 / 322 ms |
| Old GC | 0 次 | 0 次 |
| 渲染线程 CPU 时间 | 44.63 秒 | 50.67 秒 |
| 采样器探测墙钟时间 | 0.857 秒 | 0.710 秒 |

两份均有内存压力，但**没有采集区间内的 Full/Old GC**，第二份几百毫秒级的回收计数不能解释约 31 秒的上传成本。回收时间并非逐事件暂停追踪，Young/Concurrent 时间不能随意相加当作所有停顿。

第二份渲染线程 CPU 约为会话墙钟的 84.43%，相当于接近占用一个核心的大部分时间，不是整颗 8 核 CPU 总占用 84.43%。它支持检查主线程/转译提交路径，但不能替代 GPU 计时。

采样器自身探测墙钟约占会话 1.18% / 第一份 1.43%；这只衡量采样器工作，不是安全点、缓存、计时钩子等全部观察者影响。不能将诊断器下的绝对 FPS 当成完全无干扰跑分，也不能由此宣称诊断器一定只损失约 1% 性能。

## 6. 建议的处理顺序

1. **先固定场景，降低实际渲染分辨率做一份对照。** 当前窗口为 2800×1260，可先试约 1400×630（像素量四分之一，不代表 FPS 必然四倍）。使用同一位置/视角、相同时长、50 ms 采样间隔，保持其他选项一致。
2. **保持新分辨率不变，单独对照装饰性材质动画。** 重点是减少这条动态材质上传路径，不是取消技能提示或隐藏必要粒子。若收益明显，再检查具体动画、Stfu 的动画调度以及后端提交策略。
3. **测试副本中分别对照 ImmediatelyFast 与 Iris。** 一次只停用一个或调整其已确认可用的相关选项，检查依赖与画面正确性；保留 Sodium，避免同时拆掉整套渲染栈。若用其他渲染后端，只选启动器明确支持 Mali-G720 的方案，不承诺 Zink / ANGLE 必然支持或更快。
4. **之后再处理 SRE 渲染期查询和环境/声音次级负担。** SRE 可优先检查玩偶身份、手持判定和皮肤查询的重复工作。声音要先补采真正的 Sound engine；不能按当前 VoiceChat 的 100% 去删语音。
5. **内存小步对照，不盲目加大。** 先关后台，再试 2.5–3 GB 堆并观察 GC/长帧；记录未包含系统可用内存，不能直接建议分配 6–8 GB。

若场景保持不动仍复现由 60 降到 20 FPS 的走势，再单独记录温度/频率或做冷机/热机同场景对照。没有这类数据前，不把热降频作为定论。
