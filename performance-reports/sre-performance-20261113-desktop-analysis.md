# SRE4.3 电脑端性能报告分析（2026-11-13 21:50）

## 结论

**本次没有复现持续低帧：纯前台、世界内、无界面片段平均约 311.40 FPS，P99 帧间隔约 12.16 ms，最长约 41.52 ms，没有超过 50 ms 的实玩帧间隔。**

这是 Windows / RTX 2080 SUPER、开启光影的记录，不是前面的安卓 GL4ES 记录。主要成本是世界渲染、模型/方块实体及图形状态/提交；纹理上传只占全部根帧时间约 0.13%，不应沿用安卓“动态材质上传占近三成”的结论，也不应因此优先停用 Stfu。

SRE 自身有可定位的重复查询和渲染工作，值得后续定向优化，但没有依据把当前表现称为严重卡顿或认定某一款外部模组有 Bug。

### 260 配置为什么能测出 311 FPS

已读取本地 MC 1.21.1 对应的 `Minecraft.runTick` 字节码：只有 `getFramerateLimit() < 260` 时才调用 `RenderSystem.limitDisplayFPS`。因此滑块最大值 260 对应不走该常规限帧分支，不是严格锁 260 FPS。

本次普通前台帧的限帧计时为零，限帧工作出现在失焦帧。**超过 260 的平均 FPS 与本次记录不矛盾，不能据此判定采集器计算错误。**

### 当前能确认的渲染路径

```text
Iris 实体合批
  → RenderType / Shader 状态切换
  → drawElements / 顶点提交

世界模型、玩家与方块实体
  → Sodium / 原版模型绘制
  → SRE 手持、皮肤、任务提示和方块实体逻辑
```

渲染线程 CPU 时间约 105.25 秒，占会话墙钟约 **93.57% 的一个核心**。当前无限帧会尽可能跑满渲染线程，不能把这个比例解释为整颗 12 线程 CPU 占用 93.57%。GPU 执行时间没有测量，仍不能仅凭 CPU 栈断言完全是 GPU 瓶颈或完全是 CPU 瓶颈。

Dynamic Surroundings 的包含式路径达 1681/2270 个样本，是因为 `timeFrame` 等包装覆盖了大量正常世界渲染，不能解释成“动态环境消耗了 74% CPU”。其他包装器亦然。

### SRE 更值得定向优化的具体位置

1. **玩偶身份 / 背包查询**：多个手臂姿势与主副手判定路径都进入 `MorphApiClient.getDisplayedPlushStack → findIdentityPlush → collectInventories`。当前[实现](G:/exmo/StarRailExpress2/StarRailExpress/src/main/java/io/wifi/starrailexpress/plush/PlushEquipmentManager.java:63)每次收集一个临时列表并遍历背包/额外槽位。[列表构建](G:/exmo/StarRailExpress2/StarRailExpress/src/main/java/io/wifi/starrailexpress/plush/PlushEquipmentManager.java:95)直接成为 26 个渲染线程叶节点样本。服务端的 100 Tick 同步周期并不保护这些客户端渲染调用。候选方案是同玩家、同帧/同 Tick 复用查询并正确失效，而不是永久缓存装备或删掉外观功能。
2. **任务方块提示查询**：[渲染循环](G:/exmo/StarRailExpress2/StarRailExpress/src/main/java/org/agmas/noellesroles/client/TaskBlockOverlayRenderer.java:413)每帧遍历已经收集的 `taskBlocks` 表并读取 BlockState。这里不是凭空扫描整个世界，但在高 FPS 下会反复查询同一批候选。可检查刷新频率、区域筛选和状态失效，同时保留破坏修复等必要提示。
3. **小门模型、其他方块实体与文字提交**：保留的栈包含 SmallDoor / AnimatableBlockEntityRenderer，以及告示牌 `TextBatchingBuffer.flush`。当前磁盘 SRE JAR 含世界文字合批兼容类和 `signTextSource` 符号，不能简单认定没有更新优化；若要继续处理，应核对实际输入缓冲类型和兼容分支，而不是只看方法名宣称补丁失效。
4. **可见性、皮肤和装饰查询**：还有 `SackGhostClient.shouldReveal`、皮肤拥有者解析、帽子与手持物品查询等候选。它们未做独占计时，不能把 17.53% 全部算给某个函数，或承诺优化后提升同等比例的 FPS。

保留的 Top 100 栈仅覆盖渲染线程 936/2270 个样本，其他短小分散栈没有完整逐条输出；聚合热点和模组计数仍在。没有逐采样时间戳，不能用全程累计栈精确解释某一个瞬间。

## 6. 内存与声音线程

- 堆上限 **4608 MiB**，每秒快照峰值约 **2225.18 MiB（48.29%）**，本次没有堆容量紧张证据，不建议继续盲目加内存。
- 本次 Young GC 32 次 / 合计 286 ms，Concurrent GC 6 次 / 64 ms，Old GC 0 次。没有逐次暂停事件，不能把某一慢帧直接认定为 GC，也不能把并发回收时间相加当作暂停。
- 已采语音频道线程 4393/4399 个样本在等待，约 **99.86%**，不是 VoiceChat 占满 CPU。
- 真正 `Sound engine` 线程未出现在采样目标中；三个额外音频名额被名称排序靠前的音频/语音线程占用。不能进一步区分物理声效与 OpenAL 等声音内部成本。
- 采样器探测墙钟约 0.503 秒，占会话约 0.45%。这是采样器工作量，不包含所有安全点/缓存/计时钩子的观察者影响；不是“诊断器只损失 0.45% FPS”的保证。

## 7. 建议

1. **如果关注的是 CPU 占用、温度或噪音，而非更高 FPS**，可按显示器实际刷新率设置 144/165/240 等明确上限；当前 260 相当于不走常规上限。先做合理限帧，不需要先删模组。
2. **如果希望继续提高渲染性能**，先在同位置、同视角做光影开/关对照，再区分光影、驱动提交和场景内容。保留其他设置，不直接把 Iris 18.68% 当成关闭后必得收益。
3. **如果下一步改代码**，先定向处理玩偶身份重复扫描、任务方块重复世界查询，再检查模型/文字提交；需要保留装备变动、任务变化、方块更新和换世界等失效语义。当前只分析，不实施这些改动。
4. **如果实际仍有明显掉帧**，在真正复现的场景重新采集 60 秒，保持前台，尽量少开界面，用 `/sreperf mark` 标记掉帧动作。本次 120 秒因高帧率达到容量提前停止，不需要将其当成故障。

尚未完成光影/模组 A/B、GPU 硬计时或真实低帧现场复现。当前能确认的是本片段表现良好及上述热点候选，不能由此宣称所有地图和多人场景已经没有性能问题。
