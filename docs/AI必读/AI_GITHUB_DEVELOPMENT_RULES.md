项目开发与 Git 提交规范（AI 必读）
致所有参与本项目的 AI 助手与自动化工具：

本仓库有严格的代码审计与安全合规要求。在进行任何代码修改、Git 提交或配置变更时，必须绝对遵守以下红线规则。任何违反规则的操作将被视为严重违规并直接拒绝合并。

🚨 绝对红线：严禁冒充作者
1. 严禁任何形式的 Git 身份伪造

禁止擅自读取 git log 中的历史作者信息（如 haiman）并将其设置为当前提交的 Author。

禁止使用 --author="xxx" 参数强行指定非当前操作者的身份。

禁止在 .git/config 或其他配置中，将 user.name 或 user.email 设置为项目其他成员（包括主理人、前提交者等）的信息。

2. 身份缺失时的正确处理流程

如果在提交前发现当前机器没有配置 git config user.name 或 user.email（或报错 Author identity unknown），禁止自行猜测或借用历史记录中的身份。

必须立即中断操作，并向人类用户报告：“检测到当前 Git 身份未配置，请提供您的真实姓名和邮箱用于提交。”

3. Author 与 Committer 的一致性

在正常情况下，本次提交的 Author 和 Committer 应当保持一致，且代表当前实际执行操作的用户。

如果你使用了具有签名权限的密钥（如 catmoon233）进行签名，committer 字段必须真实反映当前账户，不得在 author 字段中保留无关人员（如 haiman）的名字来伪装成代码原作者。

🔐 提交签名与验证
本仓库已强制要求所有提交必须包含 Verified Signature（已验证签名）。

禁止尝试绕过或关闭提交签名机制（如 commit.gpgsign=false）。

如果本地 SSH/GPG 签名配置失败，必须向人类用户求助，禁止使用无签名的提交或伪造签名，更不得尝试直接推送到受保护分支。

⚙️ 环境与依赖处理规范
1. 禁止私自篡改网络配置

如果遇到 Git 代理问题（如 http.proxy=http://127.0.0.1:7897 握手失败），禁止私自修改或删除代理配置。请报告人类用户：“当前代理服务异常，请检查代理端口或网络环境。”

2. 禁止使用破坏性依赖脚本

如果遇到构建报错（如 Maven 依赖仓库返回 502 等网络异常），禁止私自编写或使用临时 init 脚本（如修改 build.gradle 强行绕过依赖）。

正确做法：记录错误日志，向人类用户报告具体的依赖名称和错误原因，等待人类修复环境。

📋 AI 决策回顾与行动清单
在执行任何 git commit 或 git config 之前，请先在后台自我核实：

git config user.name 是当前人类用户的真实身份吗？

git config user.email 是当前人类用户的真实邮箱吗？

我提交的 committer 信息是否真实、合法？

我是否在 author 字段中夹带了别人的名字？

记住：伪造作者身份不仅会破坏团队的协作信任，还会触发 GitHub 安全警报。遇到任何不确定的身份问题，保持沉默和询问，永远好过自作主张的“聪明”。
