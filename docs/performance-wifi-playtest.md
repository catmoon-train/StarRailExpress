## 有依据的代码优化

第一、二局 JFR 的渲染线程样本分别为 3129、2048 条，其中 90、81 条停在以下链路的配置查询处：

`ClientChunkCache → SceneAssetClient.getRemoteChunk → isFormalSceneVisible → isMovingSceneEnabled → SREClientConfig.instance → AutoConfig.getConfigHolder`

原实现对普通世界的每次区块查询先读配置，随后才判断虚拟场景区块是否存在。此次将候选区块/区段查询提前，未命中时不再读取 AutoConfig；无活动资产、空区段快照也提前返回，复用 FastUtil 空数组；可见性条件先检查运行状态与区域配置，再读取配置。

真正命中虚拟场景时仍检查原有开关、运行状态与安全区域。没有缓存可被重载/同步的配置对象，不改变场景亮度、玩家/实体可见性或区块内容。

真实隔离客户端的 `SRE_SCENE_LOOKUP_FAST_PATH_PASS checks=12` 验证：无候选时即使暂时没有配置处理器也能返回；空快照不反复分配；候选存在时可见；关闭配置、场景停止或区域未配置时仍不可见。临时伪造的候选对象只用于返回身份检查，不渲染、不加入世界，结束即恢复测试状态。

旁观阶段 JFR 中的 GC 暂停约 2.9–6.4 ms，不能据此把数百毫秒长帧统一归因于大 GC。Framepacer 等辅助模组与方块/实体/粒子渲染也出现在样本中，本轮没有无依据地批量停用它们。

**尚未取得相同前台固定路线的优化后 FPS 对比**。本轮能确认的是热点上不必要的配置查询被移除、边界行为通过真实客户端检查，不能将采样比例直接等同于 FPS 收益。

## 目标驱动游玩与聊天

用户指出随机游走不够聪明后，停止旧随机循环，改为读取自身任务、设置具体目标、定向移动并核对位置；普通聊天走原版签名聊天接口，不使用 OP 广播、不刷屏、不根据隐藏信息指认别人。

第三局发出锁匠协助邀请，服务器日志确认送达，未识别到直接回应。服务器随后自动开启额外回合；目标驱动尝试在额外的广播员回合寻找音符盒/锻炼点、尝试冥想并询问音符盒位置，第二条提问也送达但无人回应，最后正常被击杀。**没有确认成功完成这些任务**；按键保持与寻路仍不足以证明稳定的自主任务能力，不能把失败归结为已证实的游戏 API 限制。额外回合与隔离客户端测试负载不纳入上述前三局表格。
