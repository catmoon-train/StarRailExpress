# 宝可梦内存：离线证据与采集方法

## 本次能确认什么

只读统计了本机现有 Cobblemon 1.8.4、用户指定 Mega Showdown 1.3.3 与 JEI 19.70.0.469 的 JAR。检查时 `jcmd -l` 没有 Minecraft 进程，因此没有当前整包的堆直方图、保留路径或泄漏证据；不能据此断言某款模组独占多少运行内存。

| 资源 | Cobblemon 1.8.4 | Mega Showdown 1.3.3 | JEI 19.70.0.469 |
| --- | ---: | ---: | ---: |
| JAR 文件 | 133.48 MiB | 19.32 MiB | 4.63 MiB |
| ZIP 条目展开总量 | 245.01 MiB | 57.73 MiB | 9.16 MiB |
| PNG 数量 | 7,169 | 1,493 | 52 |
| 原尺寸 PNG 像素 × 4 | 283.02 MiB | 315.80 MiB | 0.42 MiB |
| 模型/动画相关条目字节 | 61.95 MiB | 38.55 MiB | 未计入此分类 |

口径：MiB=1,048,576 字节。PNG 只读文件头宽高，像素×4是假定全部按原尺寸 RGBA 同时展开的原始量，不是测得的堆/原生内存/显存，也不是下界或上界。运行时可能按需加载、释放、缩放或共享；动画裁剪、图集空隙、mipmap、资源包替换又可能改变实际量。ZIP 展开量与 PNG 解码量不能直接相加。

## 为什么禁用玩法后仍可能很大

`pokmen=false` 是运行中的玩法隔离，不是卸载 Cobblemon。为了保存和重新启用，仍保留物品/实体注册、数据与存储初始化、客户端资源注册和上游战斗引擎启动。模型 JSON 会变成带集合、字符串、骨骼和动画曲线的 Java 对象，大小不等于原文件；解码像素可能在堆外，上传后还可能占显存。

Cobblemon 内嵌 `graal-sdk-22.3.0`、`js-22.3.0`、`regex-22.3.0`、`truffle-api-22.3.0`，以及 Kotlin、ICU4J 和 MongoDB 驱动。内嵌 JAR 合计约 62.73 MiB。这证明存在脚本引擎与额外运行库来源，不证明它们实际保留了同等或更多内存，更不能单凭库名认定泄漏。

服务端还有实体的 Brain、路径、宝可梦资料、区块与存储。历史 `Ddt3meV58N` 采样曾有 691 只宝可梦、约 3,334–3,845 个总实体和 4,294–5,001 个区块；这是旧场景规模证据，不是当前状态，也不能换算单只宝可梦保留大小。刷新预算与 AI 降频减少新增与计算，不会自动删除现有实体或清空资源缓存。

## 如何用独立工具定位

安装同级 `sre-performance/build/libs/sre-performance-1.0.0.jar`；它不需要宝可梦兼容包或 SRE 本体。客户端看本地内存，服务端看服务端 JVM，远端服务器不会被客户端采集替代。详细命令和能力边界见 [工具说明](../sre-performance/README.md)。

先在资源加载完成且场景稳定后采内存快照，记录堆 used/committed/max、堆外缓冲、GC、线程、已加载区块/实体。显式执行类直方图能看到各类对象数量和浅大小，但数组、字符串、共享集合不能直接归给某款模组，且包含未回收对象。此操作可能短暂停顿，不在对局关键时刻使用。

需要调查持续增长时，在同一位置和相同玩家/实体/区块规模下，间隔采两份快照与直方图。可用 JFR 分配采样观察“哪些调用持续分配”，但它不是“哪些对象仍被引用”。不要把分配量、浅大小和 retained heap 混为一谈。

若堆使用持续增长而无法通过直方图区分引用来源，仍需明确授权后单独采堆转储，用 MAT 等检查 dominator/GC root。堆转储可能很大、暂停较长且含玩家或服务器数据，工具不默认生成、不自动上传。堆稳定而进程物理内存增长时，另查原生分配/驱动/图形资源；不能通过不断增加 `-Xmx` 解决所有问题。

本次未更改贴图、模型、玩家数据、内存分配参数或生产实例，不声称已经定位具体泄漏。
