# SRE 模型候选索引与启动实测（2026-11-07）

## 结果

新增 **模型候选索引**，不再继续调整上一轮未证明有效的 Mixin 准备过滤。该新索引保留启用；上一轮提前过滤仍默认关闭。没有删模组、改版本、增加依赖/agent、修改启动参数，或跳过皮肤模型、资源准备及烘焙。

候选查询的合成微基准证实局部 CPU 成本降低；实际完整实例通过一次冷建和四次交替热启动。但关闭组与启用组的机器负载不同，**不能把整体均值差全部归功于本补丁，也没有证明稳定的秒级整包收益**。此前 10 秒目标仍未达到。

## 为什么改这条路径

上一轮实际冷建 JFR 定位到 `GeneralModelLoadingPlugin.modifyModelOnLoad`；源码及已安装核心字节码均确认：每个顶层模型都会遍历 `BASE_MODELS` 的全部类型及基准模型，再判断命名空间、路径和阶段后缀。大多数模型并非可换肤物品，最终只是原样返回。

本轮实际运行有 21 个类型，建立 76 个索引键。初始冷建记录：

- onLoad 候选查询 **181535 次**，beforeBake 查询 **1670 次**。
- 两类回调合计命中 **66 次**，大量未命中无需再进入全部类型遍历。
- 热缓存两轮启用组均为 onLoad **34948 次**、beforeBake **1005 次**、合计命中 **66 次**。
- 索引建立观测耗时约 3.4 / 4.5 / 11.2ms；这是新增成本，不是节约的时间。

## 实现和保留的语义

全部实现位于 `sre-pack-compat`，没有重新打包或部署含大量并发用户改动的核心。

`GeneralModelLookupMixin` 在原模型插件每次初始化时建立索引，只替换两个原回调中的 `Map.entrySet()` 候选集合。**原回调的判断、`GeneralModel` 构造、返回、皮肤选择、模型依赖读取和烘焙继续执行**，不替换整个回调或模型工厂。

`ModelCandidateIndex` 按命名空间和完整的规范化路径查询：

- 只剥离一层 `item/`；onLoad 接受有/无此层前缀，beforeBake 仍要求 `item/`。
- onLoad 的空后缀始终有效；beforeBake 仅接受显式登记的阶段，包括是否登记空串。
- 生成键相撞时用原遍历顺序首项，不改成最长前缀；返回该类型原始 entry 和完整基准集合，集合内部的首匹配顺序也仍由原代码决定。
- 保留同一皮肤类型供多个物品使用，例如乘务员钥匙；弓/弩拉弦、装填、箭及烟花阶段仍按原规则。
- 每次模型重载重新建立候选表，不跨资源重载保存未烘焙/已烘焙模型、资源管理器或纹理。
- 最多处理 4096 个基准、8192 个键。超预算、构建异常或来源 Map 身份不匹配时使用原始 `entrySet()`。
- 首个就绪 tick 后停用查询计数，索引仍可用于后续模型处理；未来重载会重建，不复用旧模型对象。

钩子只针对已核对核心回调的类 SHA-256 `51f039ce121efc04381043e1ab275c6b55a46866c6b2de570998e34152447189` 启用，同时检查模组来源及类加载器实际选中资源。未知核心实现自动回原流程，避免 lambda 编号变化造成误注入。不声称支持任意其他模组对这些私有表或回调的运行时改写。

第二次关闭样本完成采集后，发现客户端已在单人世界中；立即暂停关闭动作并询问用户。用户确认正常退出后，核对进程结束、服务器停止及存档保存日志，再恢复最后一轮。该单人会话未纳入启动计时或功能验收，未强制终止客户端。

## 局部微基准（不是整包启动）

会话 scratch 中单独运行 Java 程序，仅比较本索引与等价的原候选遍历：21 类型、每类 2 个基准、512 个 ID、约 0.2% 命中，预热后各执行 50 万次查询，3 轮交替。使用当前线程 CPU 时钟，返回校验值一致；不加载 Minecraft，不更改游戏参数，且在两次完整启动之间执行，没有与热启动并行运行。

三轮观测均为原查找 **187.500ms**、索引查找 **15.625ms**。CPU 读数呈粗粒度量化，只将其解释为该合成负载下局部查询成本降低；它不包含实际游戏的全部模型构造、包装、计数、IO、线程调度与烘焙，**不得外推整包倍数或节省秒数**。
